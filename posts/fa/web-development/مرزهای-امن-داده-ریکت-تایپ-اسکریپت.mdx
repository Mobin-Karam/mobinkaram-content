یک رابط کاربری React زمانی پایدارتر و قابل‌فهم‌تر می‌شود که قرارداد روشنی داشته باشد: چه داده‌ای می‌گیرد، چه چیزی می‌تواند تغییر کند و کاربر در هر نتیجه چه چیزی می‌بیند. ساخت مرزهای امن داده در React و TypeScript فقط افزودن type به همه‌جا نیست؛ هدف این است که تصمیم‌های مهم پیش از بزرگ‌شدن یک صفحه به تجربه‌ای مبهم، دیده و قابل‌بررسی شوند.

![توسعه‌دهنده در حال کار با رایانه](https://images.unsplash.com/photo-1461749280684-dccba630e2f6?auto=format&fit=crop&w=1600&q=85)

> **وعدهٔ این مقاله:** در پایان می‌توانید مرز مسئله را تشخیص دهید، آن را با یک مدل کوچک TypeScript بیان کنید و برای حالت‌های در حال بارگذاری، خالی، خطا و موفقیت، تجربه‌ای عمدی بسازید.

## از مسیر کاربر شروع کنید

پیش از نام‌گذاری یک type، مسیر را با زبان ساده بنویسید. کاربر صفحه را باز می‌کند، برای تصمیم‌گیری زمینهٔ کافی می‌بیند، کاری انجام می‌دهد و بازخورد فوری می‌گیرد. ممکن است برنامه در انتظار پاسخ باشد، کاربر مجاز نباشد یا داده ناقص و قدیمی برگردد. این‌ها حالت‌های محصول هستند، نه اتفاق‌های فرعیِ پیاده‌سازی.

یک کامپوننت خوب در React این مسیر را قابل‌دیدن می‌کند. props آن می‌گویند والد چه چیزی می‌تواند بدهد؛ state فقط اطلاعاتی را نگه می‌دارد که بین renderها باید به خاطر سپرده شوند؛ و handlerها عمل‌هایی را توصیف می‌کنند که آن وضعیت را تغییر می‌دهند. وقتی مدل کوچک باشد، بازبینی طراحی دقیق‌تر می‌شود: هم‌تیمی می‌تواند یک شاخهٔ جاافتاده را ببیند، نه اینکه از میان چند boolean پراکنده حدس بزند.

## یک قرارداد باریک تعریف کنید

نام‌ها باید مفهوم محصول را نشان دهند، نه میان‌بری فنی مانند `data` یا `value`. وقتی گونه‌ها تعیین می‌کنند چه چیزی اجازهٔ render دارد، از union کوچک استفاده کنید. TypeScript بعد از بررسی discriminant مقدار را باریک می‌کند؛ بنابراین شاخهٔ موفقیت بدون optional chaining دفاعی، دادهٔ درست را دارد.

```tsx
type Result<T> =
  | { ok: true; value: T }
  | { ok: false; message: string };

async function getProject(id: string): Promise<Result<Project>> {
  const response = await fetch(`/api/projects/${id}`);
  if (!response.ok) return { ok: false, message: 'Project could not be loaded.' };
  return { ok: true, value: await response.json() as Project };
}
```

این نمونه عمداً render را از دریافت یا تغییر داده جدا نگه می‌دارد. نتیجه، viewی است که آسان‌تر آزموده می‌شود و بی‌صدا به لایهٔ شبکه، cache و notification تبدیل نمی‌شود. props عمومی را کم نگه دارید. اگر فراخواننده‌ها همیشه یک بستهٔ بزرگ از مقادیر را می‌فرستند، شاید کامپوننت بیش از اندازه به جزئیات والد وابسته است.

## برای هر حالتِ دیده‌شدنی تصمیم بگیرید

رابط واقعی فقط مسیر خوش‌حال ندارد. هنگام انتظار، layout را حفظ کنید تا صفحه نپرد. وقتی داده‌ای نیست، بگویید این حالت عادی است یا نه و گام بعدی مفیدی پیشنهاد دهید. هنگام خطا، پیامی آرام و انسانی نشان دهید و جزئیات فنی را جداگانه log کنید. پس از موفقیت، تغییر را در همان بخش صفحه قابل‌مشاهده کنید.

این نتیجه‌ها را با `isLoading`، `hasError` و `data` نامرتبط مدل نکنید، مگر اینکه هر ترکیب واقعاً معنی داشته باشد. flagهای متناقض صفحه‌های متناقض می‌سازند: spinner روی خطای قدیمی یا دکمه‌ای که آزاد به نظر می‌رسد اما درخواست هنوز در راه است. union تفکیک‌شده یا actionهای reducer معمولاً صادقانه‌ترند، چون ترکیب‌های مجاز را مشخص می‌کنند.

## رویدادها را نزدیک به نیت نگه دارید

نام handler در React باید نیت را بگوید: `saveProfile`، `choosePlan` یا `removeItem`. می‌توان قواعد ارزانِ سمت کاربر را برای بازخورد سریع بررسی کرد، اما مجوز، قیمت، موجودی و اعتبارسنجی پایدار باید در سرور باشد. حتی وقتی TypeScript پاسخ موردانتظار را type کرده است، پاسخ شبکه را در زمان اجرا غیرقابل‌اعتماد بدانید. type از کدی که می‌نویسید محافظت می‌کند؛ اعتبارسنجی runtime از مرزی محافظت می‌کند که در کنترل شما نیست.

برای تعامل دسترس‌پذیر، ابتدا از عنصرهای native استفاده کنید. button واقعی، کار با صفحه‌کلید، focus و معناشناسی موردانتظار را همراه دارد. label را به input متصل کنید، خطا را با متن توضیح دهید و پس از خطای ارسال، focus را روی کار نگه دارید. type به‌تنهایی ویژگی دسترس‌پذیری نیست، اما قرارداد شفاف باعث می‌شود نیازهای دسترس‌پذیری کمتر فراموش شوند.

## ترتیب عملی پیاده‌سازی

1. چهار خروجی قابل‌مشاهده را رسم کنید: آغاز، انتظار، خطا و موفقیت.
2. کوچک‌ترین type را بنویسید که ترکیب‌های ناممکن را حذف کند.
3. ابتدا view موفقیتِ ثابت را با heading، label و متن خالیِ معنی‌دار بسازید.
4. شاخه‌های انتظار و خطا را بدون تغییر سلسله‌مراتب layout اضافه کنید.
5. مرز سرور را متصل و payload آن را در runtime اعتبارسنجی کنید.
6. مسیر فقط‌با‌صفحه‌کلید، شبکهٔ کند و retry را امتحان کنید.

این ترتیب از دام رایجِ بهینه‌کردن درخواست پیش از تصمیم دربارهٔ تجربهٔ کاربر در زمان ابهام جلوگیری می‌کند. همچنین روشن می‌کند که آیا کامپوننت اصلاً به state محلی نیاز دارد یا مقدار می‌تواند هنگام render محاسبه شود.

## اشتباه‌های رایج

**استفاده از `any` در مرز.** API ناشناخته را ظاهراً آسان می‌کند، اما ابهام را به همهٔ مصرف‌کننده‌ها می‌فرستد. parser یا adapter را نزدیک درخواست بسازید.

**ارسال یک شیء props خیلی بزرگ.** این کار child را به جزئیات پیاده‌سازی والد گره می‌زند. فقط اطلاعات و callbackهای لازم را ارسال کنید.

**یکی‌گرفتن promise با قطعیت.** پاسخ typeشده هم ممکن است reject شود، timeout داشته باشد یا JSON خراب برگرداند. برای UI راه بازیابی بسازید.

**پنهان‌کردن خطا.** پنل خالی، error state دوستانه نیست. به کاربر بگویید چه کاری می‌تواند انجام دهد.

## چک‌لیست بازبینی

- آیا خواننده می‌تواند همهٔ حالت‌های قابل‌مشاهده را نام ببرد؟
- آیا type حالت‌های متناقض را حذف می‌کند؟
- آیا labelها، خطاها و عمل‌ها با صفحه‌کلید و screen reader قابل‌استفاده‌اند؟
- آیا سرور همچنان مرجع تصمیم‌های حساس است؟
- آیا دادهٔ غیرقابل‌اعتماد پیش از رسیدن به presentation بررسی می‌شود؟
- آیا توسعه‌دهندهٔ دیگر با خواندن props و state type، کامپوننت را می‌فهمد؟

## گام بعدی

این الگو را ابتدا روی یک صفحهٔ موجود اجرا کنید، نه با بازنویسی کامل یک feature. از مرزی شروع کنید که ابهام وارد برنامه می‌شود، یک مدل وضعیت صریح اضافه کنید و ببینید چه فرض‌هایی آشکار می‌شوند. هدف abstraction حداکثری نیست؛ هدف رابط وبی است که با شبکهٔ کند، دادهٔ عجیب و تغییر feature در ماه بعد هم قابل‌فهم بماند.

## یک سناریوی واقعی را دنبال کنید

یک API پروژه را تصور کنید که تیم دیگری نگهداری می‌کند. client منتشرشده ممکن است فیلد nullable تازه، پاسخ cache قدیمی، صفحهٔ خطای HTML از proxy یا پاسخ موفقی بگیرد که عضو تو در توی آن ناگهان وجود ندارد. assertion TypeScript بعد از response.json هیچ‌یک از این مقدارها را امن نمی‌کند.

## مدل را به تصمیم‌های محصول وصل کنید

دادهٔ بیرونی را یک‌بار و نزدیک شبکه adapt کنید. فیلدهای لازم را parse کنید، فقط جایی که سیاست محصول اجازه می‌دهد default مستند بدهید و نتیجه‌ای برگردانید که باقی feature آن را می‌فهمد. به این ترتیب نام‌گذاری remote، قالب تاریخ و پاسخ ناقص وارد button، card و heading نمی‌شود.

## از render برای توضیح استفاده کنید

برای مرز داده لازم نیست از روز اول abstraction بزرگی بسازید. ابتدا یک مسیر رایج و یک مسیر شکست را انتخاب کنید. heading باید هدف صفحه را بگوید، کنترل‌ها باید نامی قابل‌فهم داشته باشند و متن راهنما باید پیش از آنکه کاربر به خطا برسد تصمیمش را آسان کند. سپس با همان مدل کوچک، شاخه‌های بعدی را اضافه کنید.

## داده و رفتار را جدا کنید

render جای پنهان‌کردن تصمیم‌ها نیست. اگر نتیجهٔ یک action هنوز معلوم نیست، وضعیت pending باید در همان ناحیه قابل‌دیدن باشد. اگر نتیجه برگشت‌پذیر نیست، پیش از عمل توضیح بدهید چه رخ می‌دهد. اگر کاربر حق انجام عمل را ندارد، دلیل و راه مناسب را نشان دهید؛ پنهان‌کردن بی‌صدا معمولاً به سردرگمی و درخواست پشتیبانی منتهی می‌شود.

## کیفیت تجربه را اندازه بگیرید

مرزهای feature را حفظ کنید. component ارائه‌دهنده نباید دربارهٔ جزئیات انتقال شبکه بداند و adapter شبکه نیز نباید متن دکمه را تعیین کند. typeها می‌توانند بین این دو توافق ایجاد کنند: لایهٔ داده نتیجهٔ محدود و قابل‌اعتماد می‌دهد و لایهٔ view آن را به زبان انسانی، ساختار معنایی و عمل قابل‌دسترسی تبدیل می‌کند.

## پرسش‌های جلسهٔ بازبینی

عملکرد را پس از درستی بررسی کنید. اندازه‌گیری کنید که چه چیزی واقعاً کند است، سپس render اضافی یا کار تکراری را هدف بگیرید. memoization بدون مشاهده اغلب قراردادها را پیچیده‌تر می‌کند. رابط سریع، فقط عدد benchmark نیست؛ باید کاربر را از انتظارِ بی‌خبر، پرش layout و از دست‌رفتن ورودی نیز نجات دهد.

## تمرین کوتاه

adapter را با دادهٔ درست، فیلد حذف‌شده، نوع پایهٔ نادرست، status خطا و درخواست لغوشده آزمایش کنید. assertion مهم فقط throw شدن parser نیست؛ مهم این است که صفحه وضعیت امنی با زبان انسانی بگیرد، نه exception مربوط به انتقال شبکه.

## با شواهد منتشر کنید

پیش از انتشار، بنویسید چه چیزی واقعاً بررسی شده است. بازبینی ایستا می‌تواند حضور نام‌ها، typeها و branchها را تأیید کند. component test می‌تواند نشان دهد پس از یک action وضعیت قابل‌مشاهده ظاهر می‌شود. بررسی در مرورگر می‌تواند ترتیب focus، layout واکنش‌گرا و رفتار کنترل‌های واقعی فرم را تأیید کند. تست سرور می‌تواند نشان دهد عمل محافظت‌شده وقتی فراخواننده صفحه را دور می‌زند نیز محافظت‌شده می‌ماند. این‌ها ادعاهای متفاوت‌اند و به شواهد متفاوت نیاز دارند.

به‌جای وعدهٔ مبهمِ تست همه‌چیز، یک ماتریس کوچک تست بسازید. مسیر موفق معمولی، انتظار یا شبکهٔ کند، نتیجهٔ خالی، خطای قابل‌بازیابی، خطای مجوز و viewport باریک موبایل را وارد کنید. اگر کنترل تعاملی است مسیر مرورگر و فناوری کمکی را هم بیفزایید. این ماتریس با تغییر feature هم مفید می‌ماند، چون نتیجه‌هایی را مستند می‌کند که نباید بی‌صدا regress شوند.

## بدون حدس debug کنید

وقتی صفحهٔ React رفتاری غیرمنتظره دارد، پیش از افزودن workaround مدل وضعیت را بررسی کنید. بپرسید کدام event رخ داده، کدام مقدار عوض شده، کدام branch render باید دنبال شود و کدام بخش صفحه این نتیجه را به کاربر می‌گوید. context تشخیصی ساخت‌یافته را بدون دادهٔ شخصی log کنید. اگر مشکل در مرز remote است، identifier امن درخواست و دستهٔ پاسخ را نگه دارید، نه جزئیات داخلی را در رابط نشان دهید.

عادت مفید در debugging این است که مسئله را به دنباله‌ای قابل‌بازتولید کاهش دهید. از صفحهٔ تازه شروع کنید، action دقیق و تغییر دیداری مورد انتظار را بنویسید و سپس وضعیت واقعی را ثبت کنید. این کار مانع می‌شود session قدیمی مرورگر، پاسخ cache یا تعامل نامرتبط بخشی از توضیح شود. وقتی دنباله روشن شد، مدل یا مرز را بهتر کنید، نه اینکه فقط symptom را پنهان نمایید.

## ایدهٔ مقاله را در کد نگه دارید

با بزرگ‌شدن feature، فقط چون props اولیه شبیه‌اند یک کامپوننت را کپی نکنید. وقتی معنا و رفتار واقعاً مشترک‌اند primitive را reuse کنید؛ وقتی مسیر کاربر فرق دارد feature component تازه بسازید. typeها را نزدیک featureی نگه دارید که تصمیم را مالک است و فقط قرارداد پایداری را صادر کنید که feature دیگر لازم دارد. این کار coupling تصادفی را محدود و redesign آینده را کم‌خطرتر می‌کند.

انتخاب غیرآشکار را کنار کد مستند کنید: چرا یک وضعیت جداست، چرا بررسی سرور لازم است یا چرا action عمداً در دسترس نیست. توضیح کوتاه با دلیل محصول از کامنتی که syntax را تکرار می‌کند ماندگارتر است. بهترین کد React و TypeScript همان داستانی را می‌گوید که صفحه می‌گوید: چه کسی می‌خواهد چه کاری کند، چه چیزهایی ممکن است رخ دهد و برنامه چگونه پاسخ می‌دهد.

## نتیجهٔ نهایی

ارزش TypeScript در React دیوار بزرگی از annotationها نیست. ارزش آن مجموعهٔ کوچک‌تری از حالت‌های معتبر و گفت‌وگوی روشن‌تر دربارهٔ بقیه است. این دقت را با بازخورد صادقانه، کنترل‌های native دسترس‌پذیر، مرجعیت سرور و عملکرد اندازه‌گیری‌شده ترکیب کنید. نتیجه صفحه‌ای است که برای توسعه‌دهنده آسان‌تر تغییر می‌کند و برای همه آرام‌تر استفاده می‌شود.
