A component API is a promise to the people who will use it. In React, TypeScript lets that promise live next to the component instead of only in a design document.

## Start with the smallest useful props

Describe the values a component truly needs. Prefer a narrow union over a broad string when the valid choices are known.

```tsx
type ButtonProps = {
  tone?: "primary" | "quiet" | "danger";
  loading?: boolean;
  children: React.ReactNode;
};
```

This gives editors useful autocomplete and prevents accidental unsupported variants.

## Model related states together

Avoid combinations such as `loading`, `error`, and `success` booleans when only one can be active. A discriminated union makes impossible UI states unrepresentable.

```tsx
type SaveState =
  | { status: "idle" }
  | { status: "saving" }
  | { status: "failed"; message: string };
```

## Keep native behavior available

When wrapping a native button or input, extend its native props and forward the ref. Users retain keyboard behavior, accessibility attributes, and familiar event types.

A good component type is not decoration. It documents intent, catches misuse early, and gives refactors a safer path. Start small, name states clearly, and let the public API reflect the user experience.
