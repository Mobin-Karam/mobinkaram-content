Refactoring is changing the structure while preserving the behavior people depend on. TypeScript is especially valuable here because it turns many forgotten call sites into visible compiler errors.

## Protect the current contract

Before moving code, identify component props, exported hooks, route behavior, and API payloads. Public contracts should change only deliberately. Add or review tests around the behavior that matters most.

## Change one seam at a time

Extract a pure helper, give it a focused type, update its callers, and run checks. Small commits are easier to inspect and easier to reverse than a broad rewrite.

```ts
function formatPrice(cents: number, currency: string): string {
  return new Intl.NumberFormat("en", { style: "currency", currency }).format(cents / 100);
}
```

## Let types reveal assumptions

When a refactor produces type errors, do not silence them with casts. They often expose a missing loading state, an optional value, or an unclear ownership boundary.

The safest refactor has a narrow purpose, observable validation, and no accidental behavior change. TypeScript does not replace judgment, but it makes that judgment easier to verify.
